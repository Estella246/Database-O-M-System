# 从 Prompt 到工程化：一次 AI 驱动全栈交付的实践复盘

## 摘要

这是一次完整的 AI 协作开发实践：在同一项目中覆盖前端、后端与数据库改造，并持续交付可运行版本。实践结论很明确：  
**AI 的产出上限取决于模型能力，但交付下限取决于工程约束。**  
当协作方式从“即时 Prompt”升级为“Rule + Skill”后，代码一致性、回归稳定性与跨层联动准确率显著提升。

## 1. 项目背景与问题定义

项目类型为流程型运维工单系统，核心特征是“节点流转 + 历史可追溯 + 多端状态一致”。  
这类系统的难点不在单点功能，而在以下三个方面：
- 前后端流程语义必须一致，否则 UI 与真实状态脱节。
- 多节点字段存在继承/覆盖关系，数据口径容易漂移。
- 数据库改动频繁，若缺少审计机制，环境会快速失真。

因此，本次复盘的重点不是“如何让 AI 写出一段代码”，而是“如何让 AI 持续交付正确代码”。

## 2. 技术基线与协作原则

技术栈（简化）：
- 前端：单体页面逻辑，承载工作台、详情、主页等关键视图。
- 后端：Python + FastAPI，承担流程状态与数据口径的权威判定。
- 数据库：PostgreSQL 迁移体系，配套变更同步日志。

协作原则（实践后固化）：
- **先定义语义，再生成代码**：所有关键需求先转为 Rule。
- **先约束边界，再执行改动**：复杂任务通过 Skill 编排执行链路。
- **先验证主干，再扩大改动**：坚持小步提交与分层校验。

## 3. 方法演进：三阶段协作模型

### 阶段 A：Prompt 直驱
适用于快速起步，但存在三类共性问题：口径不稳定、风格不一致、跨模块联动易断裂。

### 阶段 B：Rule 约束化
将反复出现的偏差沉淀为规则文件，明确“必须做/禁止做/如何回退”。  
收益是把经验从“个人记忆”转为“项目机制”。

### 阶段 C：Skill 流程化
把多步骤任务封装成可复用执行路径，绑定输入、步骤、验证、失败策略。  
收益是减少遗漏，提升复杂需求的一次通过率。

## 4. Rule 体系：把业务语义变成机器可执行约束

### 4.1 设计准则
- **语义优先**：先定义业务真值，再约束实现细节。
- **可验证**：每条规则都必须对应明确检查项。
- **低歧义**：规则文本中避免“视情况而定”。
- **跨层一致**：前端展示、后端聚合、统计导出共用同一口径。

### 4.2 代表性规则实践

1) 编号规则  
统一工单编号格式，并明确服务端落库为最终真值。  
价值：避免历史格式扩散，降低并发与会话映射风险。

2) 历史节点展示规则  
要求已流转节点必须可查看历史字段，不允许以通用占位文案替代真实数据。  
价值：保障审计可读性与流程可追踪性。

3) 继承字段归并规则  
同一字段在多节点重复出现时，统一按流程后序节点优先，而非简单时间覆盖。  
价值：统一详情、列表、统计、导出口径，减少“同数不同义”。

4) SQL 同步规则  
每次迁移或手工 SQL 执行后，必须追加数据库同步日志并标注时间与来源。  
价值：形成可追溯的数据库变更链路，降低环境漂移风险。

5) UI 克制规则  
禁止无需求依据的展示增量与操作控件扩写。  
价值：抑制“AI 过度优化界面”导致的信息噪音。

## 5. Skill 体系：把复杂任务变成标准执行链路

Skill 的定位不是替代规则，而是执行规则。它适合处理“跨层联动 + 多步骤 + 高回归风险”的改动。

一个有效 Skill 通常包含五个部分：
- 触发条件：何时必须启用。
- 前置条件：运行环境、数据假设、依赖服务。
- 执行步骤：前端、后端、数据库按层拆解。
- 验证清单：主链路、边界态、失败态。
- 失败策略：回退点与影响面控制。

在流程详情场景中，Skill 将“节点高亮、可编辑性、字段显隐、数据来源、验证项”统一绑定，显著减少“只修 UI 不修语义”的问题。

## 6. 分层复盘：前端、后端、数据库

### 6.1 前端：控制大文件改动的副作用
- 先改状态语义，再改视觉表现，最后补空态与异常态。
- 任何显示规则都需可追溯到需求或 Rule，避免超范围输出。
- 路由、标签、状态三者必须同构，避免页面行为漂移。

### 6.2 后端：单一真值来源
- 当前节点、可编辑性、历史数据读取统一由后端状态驱动。
- 前端不承载流程真值推断，仅做渲染与交互编排。
- 关键 ID 以服务端返回结果为准，避免前端本地假设导致状态分叉。

### 6.3 数据库：建立审计闭环
- 迁移脚本负责结构演进与执行顺序。
- 同步日志负责跨环境可追溯与回放依据。
- 差异方言必须显式标注，禁止隐式兼容假设。

## 7. 标准执行流程（可复用）

建议将每次需求实现固定为六步：
1. 语义澄清：定义边界、异常、回退。
2. 规则落地：先补 Rule，再动代码。
3. 流程编排：复杂任务启用 Skill。
4. 分层改动：前端/后端/DB 小步推进。
5. 分层验证：功能、数据、回归三线并行。
6. 经验沉淀：将本次偏差写回 Rule/Skill。

该流程的关键价值是把“临场发挥”替换为“机制交付”。

## 8. 质量与风险控制框架

必做校验：
- 语义正确：是否满足业务口径与规则要求。
- 结构稳定：是否破坏路由、状态与依赖关系。
- 数据一致：是否影响聚合、统计、导出结果。
- 运行可用：关键接口与核心页面可回归通过。

高风险区域：
- 流程节点状态判定。
- 多节点继承字段覆盖。
- 编号生成与历史映射。
- SQL 迁移与同步日志一致性。

## 9. 对外可迁移的实践结论

### 结论一：先规则化，再 AI 化
没有规则体系时，AI 只能加速试错；有规则体系后，AI 才能加速交付。

### 结论二：后端真值优先于前端表现
流程型系统中，UI 的正确性来自状态语义，而不是组件复杂度。

### 结论三：数据库变更必须“执行 + 留痕”双轨并行
只执行不留痕，会在中长期形成不可见的技术债。

### 结论四：Skill 是复杂需求的一致性放大器
Skill 让多步骤任务具备可复现性，是团队规模化协作的关键资产。

## 10. 下一步优化方向

- 将 Rule 分级为“强制规则 / 推荐规则”，降低维护成本。
- 建立统一验证模板，把测试结果纳入交付物而非口头说明。
- 将高频需求沉淀为场景化 Skill，持续提升一次通过率。

最终目标不是“让 AI 写更多代码”，而是“让 AI 在工程体系内稳定交付正确代码”。
