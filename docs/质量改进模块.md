# 质量改进（QI）模块 Wiki

> 新版质量改进系统：5 阶段审批工作流（提出 → 评审 → 确认 → 实施 → 验收），独立 `qi_*` 表族，与旧 `requirement` 单表共存。本文覆盖模块的全部设计与实现。

---

## 1. 概述

- **定位**：对运维过程中沉淀的改进诉求进行结构化、可流转的质量改进管理。每条改进建议（主诉求单）走完整 5 阶段审批闭环。
- **与旧系统的关系**：旧「需求管理」(`requirement` 单表) 保留共存；新版用独立 `qi_*` 表族。旧数据可一键迁移到新版（见 §12）。
- **入口**：
  - 侧栏「质量管理 → 质量改进」（路由 `/qi`，路由键 `qi:manage`）。
  - 工单流程中「新增改进建议」（见 §13 工单集成）。
- **技术栈**：FastAPI（`backend/routers/qi.py`）+ 无构建 ES Modules 前端（`frontend/modules/pages/qi-page.js` 等）+ PostgreSQL（JSONB 存阶段字段）。

---

## 2. 工作流

单链 5 阶段，支持正向流转、打回、关单：

```
提出(propose) ──提交评审──▶ 评审(review)
                              │
              ┌───────────────┼────────────────┐
        评审通过              评审不通过(关单)
              │                                ▼
              ▼                             __closed__
        确认(analysis)
              │
        ┌─────┴──────┐
    分析接纳      分析不接纳(打回评审)
        │
        ▼
    实施(closure) ──提交验收──▶ 验收(acceptance)
                                   │
                          ┌────────┴────────┐
                    验收通过            验收不通过(打回实施)
                          │
                          ▼
                       __closed__
```

| 阶段 | 键 | 中文 | 处理人字段 | 关键动作 |
|---|---|---|---|---|
| 提出 | `propose` | 提出 | `proposer`（提出人） | 提交评审 |
| 评审 | `review` | 评审 | `reviewer`（提出阶段指定） | 评审通过 / 评审不通过(关单) |
| 确认 | `analysis` | 确认 | `qi_stage.responsible`（评审填，继承） | 分析接纳 / 分析不接纳(打回评审) |
| 实施 | `closure` | 实施 | `qi_stage.responsible` | 提交验收 |
| 验收 | `acceptance` | 验收 | `proposer`（验收人=提出人） | 验收通过(关单) / 验收不通过(打回实施) |

- **流转路由**：`QI_HANDLE_MODE_ROUTE`（`backend/qi_config.py` / `frontend/modules/constants/qi.js`）。
- **关单动作**：`QI_CLOSE_HANDLE_MODES = {验收通过, 评审不通过}` → `current_status=closed`，单据锁定不可再改。
- **打回动作**：`QI_REJECT_HANDLE_MODES = {分析不接纳, 验收不通过}` → `current_stage` 回退到前序阶段，新建阶段实例 `sequence+1`（旧行保留审计）。
- **草稿**：提出阶段可保存草稿（`current_status=draft`），不进入评审；工单里创建的改进建议默认为草稿，运维闭环时批量提交（见 §13）。

## 3. 数据模型

迁移：`db/migrations/0100_qi_workflow.sql`（核心 6 表）、`0101_qi_reviewer_candidates.sql`（评审人白名单）、`0102_qi_analyst_candidates.sql`（分析人白名单）。

### 3.1 `qi_request` — 主诉求单（全流程不变量）
| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGSERIAL PK | |
| qi_no | VARCHAR(32) UNIQUE | 编号 `ZLGJ-YYYYMMDD-NNN` |
| category | VARCHAR(64) | 分类 |
| proposer | VARCHAR(256) | 提出人「姓名 账号」 |
| title | TEXT | 改进标题（由旧 VARCHAR(512) 迁移 0104 改为 TEXT，防越界） |
| related_ticket_no | VARCHAR(64) | 关联运维系统单号（YW 单号） |
| description | TEXT | 详细描述（富文本） |
| expected_goal | TEXT | 改进诉求（富文本） |
| priority | VARCHAR(8) | 优先级 高/中/低（CHECK） |
| domain | VARCHAR(128) | 领域 |
| module_feature | VARCHAR(256) | 模块&特性（级联路径，如 `驱动/JDBC`） |
| planned_version | VARCHAR(128) | 计划版本 |
| reviewer | VARCHAR(256) | 评审人（提出阶段指定） |
| current_stage | VARCHAR(16) | 当前阶段（CHECK 5 选 1） |
| current_status | VARCHAR(16) | draft/in_progress/rejected/closed（CHECK） |
| creator_id / creator_name | VARCHAR | 创建人（账号 / 姓名 账号） |
| created_at / updated_at | TIMESTAMPTZ | |

> 迁移 `0104_qi_request_title_text.sql`：`title` 由 `VARCHAR(512)` 改为 `TEXT`，从根本上避免旧数据迁移/长标题越界。

### 3.2 `qi_stage` — 阶段实例
`request_id` 关联主单；`stage_key` + `sequence`（打回重进递增）；`status`（pending/in_progress/completed/rejected）；`responsible`（责任人，评审填、分析/实施继承）。

### 3.3 `qi_stage_data` — 阶段字段值
每阶段字段集不同，`values_json`（JSONB）存储；`amended`（补录）、`draft`（草稿/仅保存未流转）、`created_by`。`stage_id`/`request_id` 双 FK（级联删主单）。

### 3.4 `qi_progress_item` — 进展子项
按阶段记录进展（content + 提交人 + seq）。索引 `(stage_id, seq)`。

### 3.5 `qi_flow_log` — 流转日志
`action`（created/submitted/rejected/closed/updated/migrated）+ `from_stage`/`to_stage`/`changed_fields`/操作人/备注。

### 3.6 `qi_no_seq` — 编号序列
`(seq_key='QI', year_part=YYYYMMDD, last_suffix)`，按天计数 001–999。

### 3.7 白名单与配置表
- `qi_reviewer_candidates(account)` — 评审人白名单（`0101`）。
- `qi_analyst_candidates(account)` — 分析人白名单（`0102`）。
- `qi_closure_progress(closure_method, stage_name, sort_order)` — 闭环进展阶段配置（问题单闭环/需求闭环 的进展项）。

## 4. 编号规则

- **格式**：`ZLGJ-YYYYMMDD-NNN`（如 `ZLGJ-20260714-007`），**每天独立从 001 起、3 位**。
- **并发安全**：`pg_advisory_xact_lock` 串行化分配；递增查 `qi_request` 防历史脏号占用，1–999 循环，当日满 999 报错。
- **实现**：`backend/utils/qi_no.py:allocate_qi_no`，亚洲/上海时区取当天。
- **草稿占位**：草稿单不分配 ZLGJ 编号，提交时统一分配。

前后端共用，源：`backend/qi_config.py` / `frontend/modules/constants/qi.js`。字段类型：`text / textarea / richtext / date / select / person / cascader`。`required` 基础必填，`required_when` 条件必填。

### 提出 propose
| 字段 | label | type | 必填 |
|---|---|---|---|
| title | 改进标题 | text | ✓ |
| category | 分类 | select（定位定界/测试加固/快速恢复/需求/质量加固和改进） | ✓ |
| priority | 优先级 | select（高/中/低） | |
| domain | 领域 | select（责任田树第一层） | |
| module_feature | 模块&特性 | cascader（责任田树，根=领域子节点） | |
| related_ticket_no | 关联运维系统单号 | text（须系统内存在 YW 单号） | ✓ |
| description | 详细描述 | richtext | ✓ |
| reviewer | 下一步处理人 | person（评审人白名单） | ✓ |

### 评审 review
| 字段 | label | type | 必填 |
|---|---|---|---|
| review_result | 评审结果 | select（通过/不通过关单） | ✓ |
| responsible | 下一步处理人 | person | review_result=通过 时必填 |
| reject_reason | 评审意见 | richtext | ✓ |

### 确认 analysis
| 字段 | label | type | 必填 |
|---|---|---|---|
| accept | 是否接纳 | select（是/否） | ✓ |
| responsible | 下一步处理人 | person | accept=是 时必填 |
| review_comment | 评审意见 | richtext | ✓ |
| closure_method | 闭环方法 | select（问题单闭环/需求闭环） | accept=是 时必填 |

### 实施 closure
| 字段 | label | type | 必填 |
|---|---|---|---|
| closure_ticket_no | 问题单号/需求单号 | text | ✓ |
| progress_stage | 当前进展 | select（按闭环方法的进展项动态） | |
| closure_self_test | 闭环效果自测 | richtext | ✓ |
| accept_version | 解决版本/接纳版本 | text | ✓ |
| sla_time | SLA 时间 | date | ✓ |

### 验收 acceptance
| 字段 | label | type | 必填 |
|---|---|---|---|
| acceptance_pass | 验收是否通过 | select（通过/不通过） | ✓ |
| acceptance_conclusion | 验收结论 | richtext | ✓ |

## 6. 身份校验（提交时）

`backend/routers/qi.py:_verify_current_handler`——提交时按**当前阶段**的处理人字段校验操作人：

| 当前阶段 | 校验字段 |
|---|---|
| 提出 / 验收 | `qi_request.proposer` |
| 评审 | `qi_request.reviewer` |
| 确认 / 实施 | `qi_stage.responsible`（取最近一条 `responsible<>''`） |

- 处理人字段为「姓名 账号」格式，**取空格分隔最后一个 token 当工号**；操作人工号与之相等（或为字段任一 token）即通过，否则 403。
- 已完成阶段的**修订(amend)**：校验该阶段 `qi_stage_data.created_by`（最后提交人）+ 字段冻结规则（下游阶段已用到的字段不可再改）。

> 因此所有处理人字段必须存「姓名 账号」格式（含工号），否则提交即 403。迁移时已让 `proposer=creator_name` 保证一致（见 §12）。

## 9. 领域 / 模块&特性

来源：**责任田模块树**（`GET /api/params/duty-field/tree`），与工单「问题引入模块」同源。

- **领域**：责任田树第一层节点（如 SQL引擎）。
- **模块&特性**：**多级级联选择器**（复用工单级联组件 `renderCascadeWhitelistControl` + `bindDutyFieldCascader`），**根=所选领域的子节点（一级目录）**，逐级下钻。
  - 取值为 `/` 路径，**不含领域**（领域单独字段），如 `驱动/JDBC`、叶子 `CBB`。
  - 前端 `qi-page.js`（新建/阶段/修订三处前缀 `qi-new`/`qi-stage-propose`/`qi-amend-propose`）+ 工单弹窗 `openQiCreateModal` 两处一致复用。
  - 切换领域时按该领域 children 重根级联（保留已存模块路径）。

## 10. 闭环进展配置

「质量改进配置」页「闭环进展」：为「问题单闭环」「需求闭环」分别维护进展阶段项（顺序可调），存 `qi_closure_progress`。实施阶段的「当前进展」下拉按所选闭环方法动态取这些项。

## 11. 超期检测

- 各阶段 SLA 阈值（`QI_STAGE_SLA_HOURS`）：提出 24h、评审 48h、确认 72h、实施 168h、验收 48h。
- 列表计算 `is_overdue`：当前阶段非 closed 且 `now > sla_time`（实施阶段填的 SLA 时间）即超期。
- 列表新增「是否超期」列展示。

## 12. 旧数据迁移

「质量改进配置」页「迁移旧数据」按钮 → `POST /api/qi/migrate-legacy`（`backend/routers/qi.py:migrate_legacy`）。

- **源→目标**：旧 `requirement` 表 → 新 `qi_request`（+ qi_stage/stage_data/flow_log）。
- **只迁 5 字段**：问题描述→title、改进诉求→description、分类、优先级、提出人；reviewer 默认=提出人；关联单号/领域/模块&特性/计划版本不再迁移（留默认空）。
- **提出人=创建人**：`proposer = creator_name`（含工号、与创建人一致），不再用 `requirement.proposer`（旧库仅姓名，会导致迁移后身份校验不通过）。
- **停在提出阶段**：`current_stage=propose, current_status=in_progress`，只建 propose 阶段（不建 review），由用户手动提交评审。
- **幂等**：按 `(title, proposer, created_at)` 去重，重复迁移跳过（除非 `force=true`）。
- **超长裁剪**：title 已改 TEXT 不越界；其余 varchar 字段 `_clip` 到列上限、`_qi_priority_coerce` 归一化。
- 鉴权：`params_qi_candidates`。

## 13. 工单集成（改进建议）

工单流程的 **开发分析 / 开发闭环 / 运维闭环** 三个阶段末尾内联「改进建议」区，可直接新建改进建议：

- **草稿暂存**：工单内新建的改进建议以 `draft:true` 创建（不分配 ZLGJ 编号、不进评审），先挂在工单上。
- **批量提交**：运维闭环提交时（`saveNode` hook），自动把该工单的所有草稿改进建议**批量提交到评审**（`batchSubmitQiDraftsSilent`），分配编号、进入评审。
- 弹窗「新增改进建议」：领域/分类/优先级与新版同源（`QI_CATEGORIES`/`QI_PRIORITIES` + 责任田树级联）。
- 详情可新开页签（`qi-detail:{id}`）打开该改进单。
